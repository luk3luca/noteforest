## What changed

`block.delete` (promote and delete-subtree) and `branch.delete` (detach, and the
existing delete-subtree variant) now return a deterministic inverse. The inverse
restores the exact removed/repointed records: block IDs, content, labels,
timestamps and unknown fields; primary branch IDs, source, target, role, order
and label; chapter top-level order; anchors and reference branches; manual break
hints.

Undo and redo go through the existing phase 3a structural stack. There is no
second user-visible undo stack and no runtime stack change: the restore command
returns the original destructive command as its inverse, so a redo re-applies the
exact delete/detach with the same IDs and order.

### Inverse design: `structure.restore`

A new typed command was added because no existing command can recreate a record
with the same identity (`block.create` and `branch.create` always mint new IDs
and timestamps, and `branch.create` cannot restore top-level placement).

```ts
interface StructureRestoreCommand {
  type: 'structure.restore';
  blocks: ContentBlock[];        // full removed records
  branches: Branch[];            // full removed or repointed records
  anchors: Anchor[];             // anchors removed with their blocks
  chapters: Array<{ chapterId: string; topLevelBlockIds: string[] }>;
  manualBreakBeforeBlockIds?: string[];
  redoCommand: DocumentCommand;  // block.delete | branch.delete
}
```

- The payload is built by **diffing the pre-command and post-command
  documents** in `executeCommand`. Only removed blocks/anchors and
  removed-or-changed branches/chapters are captured, plus the exact manual-break
  list when it changed. It is therefore a targeted snapshot, not a full document
  copy.
- Surviving blocks are never overwritten, so text typed in another block between
  the delete and its undo survives. A full-document snapshot would have lost it.
- Applying the restore sets the exact branch records. For `block.delete
  promote` of a child, the command repoints the deleted block's child branches
  in place; the restore is allowed to take those branch IDs back only when the
  branch target/role still match and the restored source is one of the restored
  blocks. Any other collision is rejected with `duplicate-id`.
- The restore refuses to reinsert a block/anchor whose ID is already in use, so
  applying a stale inverse cannot duplicate records.
- `restoreRecords` returns `redoCommand` as its inverse. The phase 3a runtime
  therefore applies `delete → restore` and `restore → delete` on the same
  structural stack without knowing about the new command.
- Revision and document `updatedAt` advance monotonically on every command, as
  before. Block timestamps are restored verbatim.

The command is generated by the command layer and is not exposed in the UI.
There is no persistence-format change: commands are session-only.

## Before / after

| Area | Before 3b1 | After 3b1 |
| --- | --- | --- |
| Delete block (promote) | `inverse: null`; undo fell through to text history | Exact restore of the block, child branches, chapter order and break hints |
| Delete block (subtree) | `inverse: null`; not undoable | Exact restore of every subtree block/branch/anchor/reference record |
| Detach branch | `inverse: null`; not undoable | Exact restore of the branch record; target leaves the chapter again |
| Redo after undo | Empty redo stack for deletes | Redo re-applies the exact delete/detach (same IDs/order) |
| Undo of a creation | Applied `block.delete` but could not be redone | Redo restores the exact created block and branch IDs |
| Text after delete | n/a | Preserved by the targeted restore; only named records change |
| Runtime stacks | Structural stack for commands with inverses | Unchanged phase 3a stack; new inverse is a normal command |
| Identity | Deleted IDs lost | Block, branch, anchor IDs and unknown fields preserved |

## Tests added

### Core (`packages/core/test/destructive-undo.test.ts`, 10 tests)

- Promote a top-level block: undo restores the exact document (blocks, branch
  IDs, order, chapter, labels, unknown fields); redo reproduces the deleted
  document; three undo/redo cycles neither duplicate nor lose records.
- Promote a child: child branch IDs stay the same while repointed, then return
  to the restored parent with their original source/order.
- Delete a subtree: blocks, anchors, anchored reference branch and manual break
  hint all return exactly; repeated cycles stable.
- Detach a branch: same branch ID/source/target/role/order/label; target is a
  child again; redo detaches.
- `branch.delete delete-subtree` inverse (same generic mechanism).
- Text written in a surviving block after a subtree delete survives the undo.
- Text written in a detached target after detach survives the undo.
- LIFO: a later structural creation is undone first, then the delete restore
  still sees its pre-delete chapter snapshot.
- Restore rejects duplicate records instead of silently overwriting.
- Undo of a creation then redo returns the exact created block/branch IDs.

### E2E (`tests/e2e/m2-editor.test.mjs`, extended undo-routing test)

The existing undo-routing test now covers, in one app launch:

- delete promote → one-press undo restores blocks, arrows and IDs; redo removes
  the block again; sidebar/canvas/canonical parity at each step; persisted
  blocks/branches/chapters compared exactly with the pre-delete snapshot;
- delete subtree → undo restores all block/branch IDs and arrows; redo removes;
- detach → undo restores the exact branch record and arrow; redo detaches;
- two rapid deletes, two rapid undos and two rapid redos: one step per press,
  no dropped press, no duplicates;
- creation undo now exposes structural redo, and redo restores the same block ID;
- all previous text/structural routing, fallback, focus and one-press checks
  remain.

The test-state hook gained `branchIds` so the app-level assertions can compare
branch identity without reading only counts. No production behavior was added
for the hook.

## Known gaps

- **Phase 3b2 is untouched:** `block.move` child→top→child still recreates a
  branch with a new ID, and cross-chapter `branch.create` undo still returns the
  target to the source chapter. Those inverses remain the next phase.
- The generic diff also covers `branch.delete` with `delete-subtree`; the UI
  still only exposes detach. No new UI was added.
- Empty chapters, F3 corrupt/read-only recovery, F4 save failure, F5/F16
  keyboard/a11y, F7 stale locks, M3, and page/PDF are unchanged and out of scope.
- Text typed before a structural undo/redo is still cleared when the editor is
  rebuilt (phase 3a behavior, intentional).
- The restore payload is session-only and can be large for a very large subtree
  (one record per removed/changed entity). Commands are not persisted.
- Focus after undo returns to the phase 3a fallback (nearest surviving block or
  parent), not necessarily to the restored block. Selection/focus behavior is
  otherwise unchanged.
