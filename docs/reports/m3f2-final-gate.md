## Manifest contract

`buildExportPlan(document): ExportPlan` is pure and has no page geometry, layout,
PDF, DOM, or React dependency.

```ts
interface ExportPlan {
  entries: Array<{
    blockId: string;
    chapterId: string;
    branchId: string | null;   // incoming primary branch; null for a root
    anchorId: string | null;   // set when the branch is sourced from an anchor
    callout: boolean;          // true only for the anchored callout lane
    depth: number;             // 0 for roots
    index: number;             // reading order
  }>;
  markers: Array<{
    anchorId: string;
    blockId: string;           // anchor host block
    state: 'broken' | 'ambiguous';
    reason: AnchorResolutionReason;
    branchIds: string[];       // outgoing primary branches, branch order
    targetBlockIds: string[];  // unique, branch order
    repairFlags?: string[];
  }>;
  counts: { chapters: number; blocks: number; branches: number; markers: number };
}
```

Rules proved by tests:

1. **Outline order.** Chapters in document order; top-level blocks in chapter
   order; anchored primary children before direct primary children. Anchored
   children use the ratified D3 order: anchor content order (resolved position,
   then state/ID), then branch order.
2. **Exactly once.** Every primary block is emitted once; every primary branch
   is attached to exactly one entry; block and branch ID sets equal the
   canonical document's primary structure.
3. **Shared child once.** A shared child appears only at its primary home, even
   when several reference parents point at it.
4. **Reference neutrality.** Reference branches add no entries. Adding reference
   edges, including a reference cycle, leaves the entire manifest deep-equal.
5. **Callouts included.** An anchored primary child is an entry with
   `callout: true`; it is not omitted or duplicated.
6. **Broken/ambiguous markers.** A broken or ambiguous anchor that sources at
   least one primary branch adds one marker and its target blocks remain emitted
   exactly once. Reference-only anchors do not add markers, because that would
   make reference edges change the manifest.
7. **Deterministic.** Repeated runs, cloned documents, and reversed block/anchor/
   branch map insertion order produce the same manifest.
8. **Empty chapter.** An empty chapter contributes no entries and does not
   invent a root.

M4 must consume this ordering/marker contract rather than re-traversing with a
second resolver.

## 1,000-anchor performance

Generated document: 100 blocks, 10 anchors per block — 400 text, 300 whole
formula, 300 code-range anchors — plus one outgoing reference branch per anchor
so resolution does not short-circuit to idle.

Measured with `resolveDocumentAnchors` on the current machine:

- first run: **8.00 ms**
- second (deterministic) run: **5.19 ms**
- all 1,000 anchors resolved: `resolved=1000`, other states zero
- target: `<100 ms` — pass with roughly 12× headroom

The test is a core unit/perf guard, not critical e2e. No architectural resolver
change was needed.

## Duplicate/paste remap

`planDuplicateSubtree(document, rootBlockId, options)` returns a pure plan:

- `blockIdMap`, `anchorIdMap`, `branchIdMap` map source IDs to fresh IDs;
- `blocks`, `anchors`, `branches` are copied records only;
- text anchor marks and atomic `anchorIds` are remapped; legacy `anchorId` is
  normalized to canonical `anchorIds`;
- bindings to anchors outside the subtree are stripped and listed in
  `strippedAnchorIds`;
- internal primary branches are copied; the duplicate root's incoming edge is
  left with the original;
- internal reference branches are copied by default (`includeInternalReferences:
  false` disables them); reference branches touching the outside are recorded in
  `skippedReferenceBranchIds`, never copied;
- IDs are checked against the whole document and against the plan, with retry if
  an injected factory collides.

Tests cover shared marks, formula/code bindings, legacy binding normalization,
external reference exclusion, internal reference copying/omission, application
into a valid document, deterministic output, collision retry, and a missing root.

**Follow-up:** UI paste/duplicate placement, the command envelope, and undo are
not part of M3f2. The helper is ready for that command when the UI path is
scheduled.

## Risks and open questions

- **Manifest is structural only.** M4 must use `buildExportPlan`/the same
  resolver and add page geometry, PDF markers, page count, and the optional
  appendix. A second traversal would reopen the divergence risk in design §15.
- **Markers are primary-branch-scoped.** A broken anchor with only reference
  edges is not a manifest marker, by design: otherwise adding a reference edge
  would change the manifest. The UI can still show its health marker.
- **Segmented fixture compatibility.** Existing layout/Spike fixtures retain the
  M2 legacy `anchorId` binding because the Spike layout estimator reads that
  shape; canonical M3 fixtures use `anchorIds`. Migrating the layout estimator is
  M4 wiring work, not an M3f2 change.
- **Perf is one machine, one run.** The unit guard asserts `<100 ms`; the report
  records the measured numbers. A regression on slower hardware should be
  profiled with the same fixture before changing the resolver.
- **Duplicate helper is a plan, not a command.** Placement (chapter slot/parent),
  one-undo composite behavior, and clipboard integration are still open UI work.
