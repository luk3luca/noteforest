# B2 — contrast: the code-theme registry and the Continuous edge states

**Builder report.** One worktree, one commit. Branch `t3/b2-contrast`, based on `main` after B1.

---

## Summary

Two colour problems, one question: *which colour passes 3:1 / 4.5:1 on which surface.*

**Part A — code themes.** A registry
(`renderer/src/lib/code-themes.ts`) now holds four themes taken verbatim — **Dark+**, **Light+**,
**Monokai**, **One Light** — each with the eight syntax roles, **its own code surface**, and its own
ink for unclassified code text. The Continuous code block (and the flat Markdown guest editor) paints
that surface instead of the tinted note card, so every role is read against the background the theme
was measured on. The worst role per theme is **computed** from the registry (never typed) and shown in
a new Appearance → **Code theme** control; `appearance.codeTheme` is app-level, defaults to `auto`
(dark → Dark+, light → Light+), is additive inside `settingsVersion: 5`, and the stylesheet's four
`html[data-code-theme="…"]` blocks are proven **equal to the registry** by a unit test. Page Read/Edit
and the PDF keep their own fixed One Light roles: the paper does not move.

**Part B — Continuous edges.** The `opacity` fade is gone from the muted and reference states (path and
arrow). The muted token is retuned per polarity so **resting, reference and muted all clear 3:1 on
`--bg-canvas` at full opacity**; the reference token needed no colour change once the fade was removed.
Distinction is now hue + dash + the user's R6 widths, never fading. Page/PDF edges are untouched and the
existing isolation tests still pass unchanged.

**The default look changes**: `auto` makes Dark+ the dark code theme and Light+ the light one, and both
bring their own surface (`#1e1e1e` / `#ffffff`) instead of the note card. That is the approved design
decision; it is shown below so it can be vetoed in one line.

- The picker is a real control: selecting `Monokai` writes the setting, flips the root attribute, and

- **Page/PDF isolation, three ways**: (1) the page still renders `#f5f7f9` segments with

  change between them; (2) no Page rule reads `--code-surface`/`--code-text`, no `print.css` rule mentions

  pass unchanged, including `editor-appearance`'s raster check that the PDF still prints One Light and
  **never** Monokai.

### A5. Two additions beyond the brief's sketch (stated, not hidden)

1. **`--code-text` (the theme's own ink).** A code block contains text the grammar does not classify
   (punctuation, plain identifiers). It used to inherit `--text-1`; on a Light+ block inside a dark app
   that is light grey on white. The registry therefore carries one more documented value per theme —
   the theme's editor foreground (`#d4d4d4`, `#000000`, `#f8f8f2`, `#383a42`) — written as
   `--code-text` and used as the block's `color`. Nothing is invented: these are the themes'
   documented foregrounds. `worstContrast` includes it, so it can never silently fall below the label.
2. **The in-block chrome follows the ink.** `.nf-code-label` (the `TS` language tag) sat on `--text-3`
   and disappeared on a white block; it now uses `var(--code-text)` at 60 %. The same rule keeps the
   Appearance preview rail's code sample honest (`background: var(--code-surface)`).

**Where the brief's example numbers differ from the measurement:** the brief illustrates `Monokai · 3.44`
and `AA · 4.60`. `3.44` is Monokai's comment on *our note card*; on Monokai's **own** surface (`#272822`)
the computed worst is **3.03**, which is what the picker shows. `4.60` is Light+'s `number` role; the
worst role is `type` at **4.59**. Both are still AA. The label is computed, so the display follows the
registry rather than the illustration.

**Surfaces chosen for the classics:** Monokai `#272822`, One Light `#fafafa` — the themes' documented
editor backgrounds. Consequence: a user who picks Monokai sees the block on `#272822` instead of our card
(a one-line change in the registry if the product owner prefers the old card surface).

## Evidence — Part B (Continuous edges)

### B1. The measured table (`apps/desktop/test/appearance-css-guard.test.ts`, B2 block)

Contrast against `--bg-canvas` (`#17181a` dark, `#ffffff` light), **full opacity**:

| State | Dark before | Dark after | Light before | Light after |
|---|---:|---:|---:|---:|
| resting (`--accent-strong`, blue) | 11.19 | **11.19** | 9.30 | **9.30** |
| reference (`--edge-reference`, dashed) | 4.73 full / 3.38 at 78 % | **4.73** | 4.52 full / 3.01 at 78 % | **4.52** |
| muted (`--edge-muted`, solid) | 2.73 full / **1.35** at 35 % | **3.69** (`#6a737c`) | 2.51 full / **1.33** at 35 % | **3.71** (`#7c868f`) |

**A correction to the brief's premise.** The plan's light `reference` figure (`2.51`) is the *muted*
token at full opacity; the real shipped reference was `4.52` at full opacity and `3.01` through the
`0.78` fade. So the only state that genuinely failed was **muted** (both polarities), plus the light
reference sitting on the 3.0 line once faded. Removing the fade alone fixes the reference; the muted
token is the only colour change, and it stays below the reference in both polarities so the hierarchy
(`resting > reference > muted`) survives.

### B2. What changed in CSS

- `.nf-edge-muted` and `.nf-edge-arrow.nf-edge-muted`: `opacity: 0.35` removed.
- `.nf-edge-reference` and `.nf-edge-reference-arrow`: `opacity: 0.78` removed, `opacity` dropped from the
  transition, and the `opacity: 1` on the `-active` variants removed (dead once the base is opaque).
  `stroke-dasharray: 5 4` and the open chevron stay; a selected reference is still the accent.
- `--edge-muted`: dark `#565f68 → #6a737c`, light `#9aa5ad → #7c868f`. `--edge-reference` unchanged.
- **R6 widths and the fixed arrowhead are untouched**: 1.25 resting, 1.75 active, 1 muted, 6 × 3
  arrowhead. The UI asserts `stroke-width` 1 / 1.75 and a 6 × 6 arrow box in both polarities.

### B3. The guard and the screenshots

The UI case (`tests/ui/b2-contrast.test.mjs`) loads a document with a real reference edge over the demo
canvas and, per polarity, reads the three states from the DOM and computes WCAG contrast there:

- idle: no muted edge exists; resting = `--accent-strong`; the reference is the neutral token, opacity
  `1`, with a dash pattern; resting 11.19 / 9.30 and reference 4.73 / 4.52 (≥ 3);
- selected: muted paths exist at opacity `1`, stroke `rgb(106,115,124)` / `rgb(124,134,143)`
  (**3.69 / 3.71**), widths 1 and 1.75, arrow box 6 × 6; the reference elsewhere on the canvas stays
  neutral and ≥ 3:1;
- **density 60 %**: the muted and reference strokes and widths are byte-identical to 100 % (density is a
  Page theme and R6 owns the Continuous widths), and the 60 % screenshots below show it.

## Risks and follow-ups

1. **The classic themes carry their canonical backgrounds** (`#272822`, `#fafafa`), so choosing Monokai
   no longer paints on the note card. One line in `code-themes.ts` if the product owner wants the card
   back. Monokai's label then reads `3.44` instead of `3.03`.
2. **Mixed-polarity chrome.** Picking Light+ in a dark app gives a white code block with the shell's dark
   fence/copy chip around it (`--surface-3` / `--surface-2`). The block itself is correct and readable
   (see `code-light-plus.png`); the copy chip is a hover affordance and was left alone to keep this batch
   scoped. A follow-up could make those two chrome roles follow `--code-surface`.
3. **The light reference is unchanged at `#6c7882`.** It passes at full opacity (4.52), so no colour edit
   was made; the brief's `2.51` was the muted token. If the product owner wants the reference *lighter*
   now that it is opaque, that is a deliberate second decision, not a bug fix.
4. **Density does not affect Continuous.** The 60 % screenshots are identical to 100 % by design (density
   is a Page theme; R6 owns the Continuous widths). The brief asked for both; both were captured.
5. **Docs to refresh (not edited here)**: `docs/design/code-palette.md` (says dark = Monokai, light = One
   Light as the only palette), `docs/design-tokens-continuous.md` §Colors (still says `--edge-muted` is
   `#565f68` / `#9aa5ad` at 0.35 opacity), and `docs/design/code-themes.md` §5 items 1–3 are now shipped.
   These are design docs owned by the Planner/Orchestrator, so the Builder left them untouched.
6. **`--code-surface` has no fallback value.** If `data-code-theme` were ever absent the block would fall
   back to transparent. The attribute is written by the pre-render appearance call and by every settings
   change (`appearance.test.ts` covers the unknown-value path), so this is a theoretical state; a CSS
   fallback would be a second palette and was deliberately not added.
