# ADR-0003 — External Agent API: local HTTP + MCP, auth, locking, audit

- **Status:** Accepted
- **Date:** 3 November 2026
- **Decision owner:** Orchestrator, ratified by the product owner
- **Related:** spec §12 (External Agent API), §15.18 (AC-70–AC-74), `docs/adr/0002-pdf-pipeline.md`

## Context

V1 has no in-app agent panel. External agents (Hermes, OpenCode, scripts, MCP clients) must be able to read and mutate documents through the same typed command layer as the UI, with the same validation, undo/redo, and audit. The API is a local capability on a personal Mac, not a network service.

Threats that matter:

- a malicious website in the user's browser reaching `localhost` (SSRF, DNS rebinding, CSRF);
- a leaked token used by an unexpected local process;
- a second writer corrupting `document.json`;
- an agent applying a stale or destructive command without the user seeing it;
- audit logs or tokens leaking into the document package, git, or PDF metadata.

The product owner ratified the defaults on 3 November 2026. D16–D20 are closed.

## Decision

### Transport and process model

- **HTTP JSON is the primitive.** The server binds to `127.0.0.1` only. Default state: **off**. The user enables it in app settings and issues a token.
- **MCP is an adapter**, not a second implementation. A local MCP bridge (stdio and/or streamable HTTP) maps MCP tools to the same HTTP endpoints and command catalog. It has no extra privileges and uses the same bearer token.
- A CLI may wrap the same client. There is no privileged "internal" endpoint.
- The server runs inside the app main process (or an Electron utility process), not in the renderer. The renderer never listens on a socket.
- Port: an ephemeral localhost port by default, with an optional fixed port. The chosen port is shown in settings and in the MCP config snippet.
- No remote bind, no TLS requirement for loopback, no cloud relay, no webhook egress, no telemetry.

### Authentication and scopes

- **Bearer token** in `Authorization: Bearer <token>`. Tokens are generated by the app with at least 256 bits of entropy, formatted `nf_<tokenId>_<secret>`.
- **Shown once** at creation. The app stores only `tokenId`, a short display prefix, the scope set, the document binding, and `HMAC-SHA256(localPepper, secret)`. The plaintext token is never stored, logged, or recoverable. A lost token is revoked and reissued.
- **Revocable immediately** in app settings. Revocation invalidates in-flight requests at the next authorization check.
- **Document-scoped (D17 closed).** Each token names exactly one document ID. The server enforces the binding on every request; a token cannot read or write another document, even if the path is known. There is no library-wide token in v1. To work on another document, the user issues another token.
- **Scopes:** `read`, `write`, `export`, `destructive`, `audit`.
  - `read` — queries, layout snapshots, search.
  - `write` — non-destructive mutations, undo/redo.
  - `export` — PDF export jobs.
  - `destructive` — delete, merge, delete-subtree, chapter deletion, irreversible page-setup changes. Requires an explicit `confirm` naming the affected IDs; a dry-run is strongly recommended first.
  - `audit` — read the audit log.
  - A write token cannot grant itself `destructive`; escalation requires a new token issued by the user in the app. Token management is **UI-only** and is not exposed over the API.
- Tokens are long-lived by default with explicit revocation. Optional expiry is a future addition; if added, it must be visible in the UI and audit.
- Failed authentication is rate-limited and audited without storing the presented token.

### Loopback hardening

- Bind `127.0.0.1` (and `::1` only if explicitly enabled). Reject requests whose `Host` is not `127.0.0.1:<port>`, `localhost:<port>`, or `[::1]:<port>`.
- No permissive CORS. Do not send `Access-Control-Allow-Origin: *`. Reject browser-origin requests by default; a local CLI/MCP client sends no `Origin`.
- Mutations require `Content-Type: application/json`, a bearer token, and `POST`/`PATCH`; no state change on `GET`.
- Require a custom header (`X-NoteForest-Client: <name/version>`) for mutations; this is defense in depth against simple CSRF, not the primary auth.
- Request body limit and per-token rate limit (default 120 requests/minute, 4 concurrent; configurable). `429` with `Retry-After`.
- CSP and the app's renderer sandbox are unaffected; the API never returns executable HTML.

### Revision and single-writer lock

- `document.revision` is a persisted monotonic integer, starting at 0 and incrementing once per committed transaction.
- Every mutating command carries `baseRevision`. Apply fails with `409 revision_conflict` if the document revision moved. There is no automatic rebase in v1; the client re-reads and re-prepares.
- **One writer per document (D18 closed).** The app instance that opens the document holds an OS advisory lock on `document.json` plus a sidecar lock in app support (keyed by a hash of the document path) containing PID, host, session, and timestamp. The lock is released on close, crash recovery, or explicit user "take over."
- Concurrent readers are allowed: they open the canonical file read-only and never write.
- A second process that opens the same document is **read-only** and says so. It cannot take the write lock silently.
- The API never acquires the lock independently. Writes route to the open app instance. If no instance has the document open, mutating commands fail with `document_not_open`; v1 does not spawn a headless writer.
- External file modification (mtime/content hash) blocks writes until the user resolves reload/overwrite/save-copy as in spec §10.10.

### Commands, transactions, dry-run, undo

- The v1 surface is the **semantic command catalog** in spec §12.3 (D19 closed), not raw JSON patches. Low-level block/branch primitives stay internal and are composed into semantic commands.
- Command envelope: `id`, `type`, `version`, `actor`, `documentId`, `baseRevision`, `context`, `args`, `idempotencyKey`, `dryRun`.
- A batch is a transaction. Apply is all-or-nothing; failure leaves the document unchanged and releases no partial mutations. Every command has an inverse; multi-step operations are one undo entry.
- `dryRun: true` validates, returns a diff, affected IDs, and pagination/layout impact without writing. It is not a reservation.
- **Undo/redo:** API undo accepts a `transactionId` and a `baseRevision`. It succeeds only if that transaction is still the top undoable entry; otherwise `409 undo_unavailable`. This shares the UI session stack but prevents an agent from silently reverting unrelated user work. The API never undoes across a document reload; history is session-only.
- **Delete confirmation:** destructive commands require `confirm: { affectedIds: [...] }` matching the dry-run/result set. A mismatch fails before mutation.
- **Idempotency:** `idempotencyKey` is scoped to the token and document, retained for 24 hours; a replay returns the original result.

### PDF export API

- `export.pdf` is **job-based (D20 closed)**: it returns `202` with a job ID and a status URL. Small exports normally complete before the first poll.
- The request must specify an output path inside the user's configured export directory and an explicit overwrite flag. The API cannot write outside that directory.
- The job uses the same paginator and print compositor as the UI (ADR-0002). It never runs a second paginator.
- `no_safe_page_break` is a typed job failure with the affected block/page IDs, not a partial PDF.
- The audit entry records the job ID, output path, page count, and result; it does not store the PDF bytes.

### Audit

- Append-only JSONL in app support (`.../NoteForest/audit/`), one file per month, outside the document package and not in git.
- Every request — read, write, dry-run, export, failure, auth failure — records: timestamp, token ID/client, command/query, document ID, base revision, result, affected IDs, duration, and error code. It does **not** store secrets, full document content, or PDF bytes.
- Rotation and retention are configurable (default: 30 days or 50 MB, whichever comes first). The UI can export/clear the log.
- Audit entries are readable with `audit` scope. The log is not writable or deletable through the API.

### Errors

Typed JSON errors with a stable code and a human-readable message:

`auth_missing`, `auth_invalid`, `token_revoked`, `scope_denied`, `document_scope_mismatch`, `document_not_open`, `revision_conflict`, `validation_failed`, `confirmation_required`, `confirmation_mismatch`, `not_found`, `idempotency_conflict`, `undo_unavailable`, `rate_limited`, `no_safe_page_break`, `internal_error`.

No stack traces, absolute paths, or token material in responses.

### Non-goals

- Remote access, OAuth, cloud relay, multi-user, sync.
- An in-app agent panel, background autonomy, or agent turns.
- Token management over the API.
- Arbitrary shell, filesystem, or network tools.
- Executing document text as instructions; the API accepts typed commands only.

## Consequences

Positive:

- One command layer for UI and agents; no second mutation path.
- Document-scoped tokens and a single-writer lock make accidental cross-document or concurrent writes unlikely and detectable.
- Dry-run + confirmation + audit make destructive agent actions reviewable.
- HTTP-first keeps the server simple; MCP is a thin adapter for agent ecosystems.

Negative:

- Document-scoped tokens mean an agent working across a library needs multiple tokens; this is deliberate friction in v1.
- The API requires the document to be open in the app; headless automation is not supported in v1.
- The shared undo stack plus `transactionId` guard is more constrained than a free undo API; this is deliberate.
- Token and audit management are UI work that must ship with the API, not after it.

## Acceptance and tests

- Auth: missing/invalid/revoked token, wrong document, insufficient scope, `destructive` without confirmation, token shown once and hash-only storage.
- Loopback: non-loopback bind rejected, bad `Host` rejected, browser `Origin` rejected, oversized body rejected, rate limit returns `429`.
- Concurrency: two writers, stale `baseRevision` returns `409`, concurrent reads succeed, second process is read-only, external file edit blocks writes.
- Commands: dry-run matches apply diff, all-or-nothing batch, inverse/undo, idempotent replay, destructive confirmation mismatch.
- PDF job: status transitions, page count equals paginator, `no_safe_page_break` is typed, output path cannot escape the export directory.
- Audit: every request type logged, no secrets/content, rotation works, `audit` scope required.
- MCP: tools map to the same commands, no privileged path, same auth/scopes.

## Revisit triggers

- Cross-document or library automation becomes a real workflow (then a library-scoped token design, with an ADR).
- Remote access or multi-user collaboration is requested (separate ADR; the local API is not the base for it).
- A headless/daemon mode is required (separate ADR for locking and lifecycle).
- The MCP ecosystem standardizes a transport or auth model that changes the adapter.
